# StopWatch v1.0：PC 客户端与真实 Codex 联调

本轮使用原生 macOS Tauri 客户端、其捆绑的 Bridge 和一台 StopWatch v1.0。
接续[基础外设验收](m5stack-stopwatch-hil-2026-11-05.md)，不使用合成会话冒充
真实 Codex 状态，不以网页开发服务器代替原生客户端。

## 环境与证据

- 设备固件：0.1.1-stopwatch-dev；原生 USB Serial/JTAG，ESP32-S3 v0.2。
- 桌面源码版本：0.1.199；完整应用资源预检、前端构建、Rust 构建和 app 打包成功。
  Node、FFmpeg、原有 P4 镜像及其来源/许可证检查均保留。
- 两个真实 Codex Desktop 会话：StopWatch 联调 A、StopWatch 联调 B。
  仅执行计时、等待确认和正常结束，没有修改项目文件。
- 失败分支另用真实 `codex exec --json`，一次性 provider 配置连接本机自有
  HTTP 503 测试服务；不修改用户全局配置，不记录请求正文，不向设备直接注入 error。
- 本地原始证据保存在被 Git 忽略的 `artifacts/stopwatch/e2e/`，包含 Bridge 状态、
  CLI 退出码、USB 枚举变化和串口重开诊断。公开记录不携带其他聊天内容。

## 四项结果

| 项目 | 观察 | 结果 |
| --- | --- | --- |
| 原生客户端识别与跟随 | 自动识别 StopWatch、固件和 S3 能力；原有 Codex 通道可跟随内置小狗 | 通过 |
| 真实会话生命周期 | 工作中、已接受的异步等待确认、完成、受控失败经 Bridge 到达设备；原生诊断回读状态 | 通过，边界见下文 |
| 多会话双向选择 | 客户端选择 B 后，用户短按蓝键到 A、黄键回 B；用户确认 PC 与设备均同步变化 | 通过 |
| 断线与重启恢复 | USB 拔出超过 30 秒后用户确认旧状态清理；插回与设备电源重启均自动恢复且两端一致；修正串口控制线后客户端连续重启恢复 | 通过本轮短时复测 |

A 正常结束时，用户确认设备显示完成并有短震动。完成卡片在结束后十余秒和
约 50 秒仍可回读，之后自动消失并跟随其他会话。B 也已正常结束，两个测试计时均停止。
真实失败由 CLI 非零退出及 rollout 的 `task_complete.error` 交叉确认；客户端和
设备回读均进入出错，卡片随后自动到期，没有反复续期。

本轮等待确认验证了实际提问调用、接受回执及设备状态。B 的首次确认题没有被用户
找到，随后达到等待上限；不能把它记为用户完成了 B 的确认题。匹配答案、部分答案、
无关消息和失败提问的退场规则另有 Bridge 回归测试。

## 发现与修正

1. 多板 CMake 中 StopWatch 的版本声明早于 P4 默认版本，桌面资源预检原先误取
   第一个 PROJECT_VER。现在选择唯一的 P4 字面版本，缺失或歧义时明确失败。
2. 增加 StopWatch 会话面板，复用现有会话同步器，显示电脑选择与真实设备诊断
   回读。断线、换设备、换连接或启动标识变化时，旧诊断响应不能覆盖新界面。
3. Codex 异步问题以前可能被随后的工具/进度日志覆盖为工作中。现在关联实际调用、
   accepted 回执及对应问题答案，保留等待确认；终态清理有界跟踪。
4. 真实受控 503 曾被错误识别为完成。现在识别现代 rollout 的
   `task_complete.error`，使用失败状态和失败文案。普通工具输出不单独等同于任务失败。
5. 运行中设置的会话名称现在优先于已缓存的通用标题；索引暂缺时保留已知标题。
6. 客户端重启时曾出现设备动画继续、USB 可枚举但协议无回复。断开 USB 并断电后恢复。
   复测还发现旧串口开启顺序会触发设备重新启动。POSIX 串口现在先保留 DTR，
   清 RTS 后再清 DTR，避免在 RTS 仍置位时清 DTR 的原生 USB 复位序列。
7. 退出时曾出现“设备仍在传输数据”的保护提示。此判断使用通用 USB 传输锁，
   不足以单独证明正在刷固件；本轮没有发起 OTA 或资源写入。正常 S3 路径本来
   就不查询可配置按键，因此不能把该提示归因于按键查询。未禁用退出保护，
   具体占锁操作仍未确定；后续多次正常退出未再出现提示。
8. speaking 复用工作动画并显示正在回复；诊断补充当前会话 ID、标题和生命周期。

控制线顺序参考 Espressif 的
[ESP32-S3 技术参考手册，USB Serial/JTAG 章节](https://documentation.espressif.com/esp32-s3_technical_reference_manual_en.pdf)。
未将本次失联直接断言为某个芯片缺陷。

## 可复现验证

常规源码测试与构建方式见[板级适配说明](m5stack-stopwatch.md)。完整原生打包必须
准备项目原有桌面运行资源；不能用空 bundle resources 的编译检查替代成品验收。

有本机 Bridge 运行时，可手动执行真实失败测试：

~~~sh
python3 pc/scripts/verify-codex-failure.py \
  --output artifacts/stopwatch/e2e/local-error \
  --response-delay 30
~~~

脚本会创建真实 CLI 测试会话并打印 ID。需要从桌面队列选择它时，先通过 Codex
正常的重命名操作设置测试名称；项目原有的小列表会优先选取有名称的会话。
脚本仅连接 loopback Bridge，最长运行有界，输出目录不应提交到上游。

## 验收边界

本轮覆盖本机 macOS、本台 v1.0、内置宠物和已有 JSONL 会话链路。没有验证
Windows、长时间压力/续航、音频、自定义形象、PetUI 或 OTA；没有推送上游。
USB 曾发生一次需要断电恢复的异常，控制线修正后的短时复测未复现，仍需长期观察。
