# 实时对话桌面 Agent 工具

桌面 Agent 与家居控制、待办、电脑状态、联网检索一样，是 Pet 的工具能力。模型根据用户目标自主选择，不依赖固定口令或必须说出 Agent 名称。当前执行适配器支持 ChatGPT（Codex）及 WorkBuddy 桌面会话，不是网页 ChatGPT，也不自动新建会话或启动独立 CLI 任务；其他 Agent 不能假装已接入。

`agent` 参数只允许 `codex/workbuddy`。未点名时直接使用设备当前跟随的 Agent，无需绑定具体会话；尚未支持的跟随目标提示限制，不默认改用 Codex。Work 是 WorkBuddy 的简称，明确指定时按用户选择，不回退到另一客户端。跟随只决定默认客户端，不决定具体对话，始终发送到该客户端当前唯一可确认的主窗口。下文 Codex 的输入、草稿和权限保护同样用于 WorkBuddy。

### WorkBuddy 回执

macOS 的任务派发和按键语音共用输入框就绪检查：置前后等待编辑器稳定，WorkBuddy 空树最多恢复一次，2.5 秒就绪预算外仍受输入桥超时保护。不会因为首次扫描没有输入框就立即失败；多个候选仍不猜测选择。任务准备始终锁定原有唯一正常主窗口，每次重读检查弹窗、多窗口及窗口身份，不启动客户端或导航会话，不写草稿、不自动重试已发送任务。

使用前在 Pet Manager 启用 WorkBuddy 通道，保持状态 Hook 可用。派发、去重、状态查询和结果关联按 Agent 隔离。请求摘要来自完整 `UserPromptSubmit.prompt`；Hook 的 `generation_id` 经哈希用于匹配同轮 `Stop`。提交事件缺少该字段时继续跟踪，不提前结束监控。`PostToolUseFailure` 只表示一次工具失败，不等于整轮结束。

`Stop` 可通过本次 Hook 指定的同会话 transcript 补足关联：仅读取 WorkBuddy projects 内对应文件末尾最多 256 KiB，以完成事件的生成标识或完整回复精确匹配唯一已完成 assistant 消息，再沿最多 128 层 parentId 回溯原始 user 消息。只上报请求哈希、消息标识哈希、固定证据类型、用户消息时间及脱敏回复摘要，不导出路径、思考或工具正文。原生层仍要求派发后实际收到相同会话、相同请求哈希的提交事件，且父链用户消息不早于本次任务创建时间，才接受完成；旧回复、重复/断裂/跨会话父链或歧义均不猜测。不同任务不按“最近活跃”关联，无法证明时继续等待，最多 15 分钟后说明结果未确认，不据此建议升级客户端。

执行中追加仍依赖客户端暴露唯一可用的原生 Send/Queue/Steer 控件；不停止旧任务，不使用猜测快捷键。未启用 Hook 或未收到匹配回执时不会声称发送成功，也不会自动重发。

## 使用

1. 打开 Codex 的目标会话，输入框不要留草稿；执行中也可追加新请求。
2. 保留一个 Codex 主窗口，打开要接收任务的对话即可；不需要在 Pet Manager 另选或绑定会话。Mac 需要已有的辅助功能授权。
   macOS 自动忽略非模态辅助窗口，只定位正常对话主窗口；无需手动关闭应用自带的辅助窗口。真正的模态弹窗仍需先处理，避免绕过授权或误操作。
3. 进入宠物实时对话，直接说「把桌面的会议记录整理成文档」或「帮我修复当前项目的测试」。Pet 判断需要电脑能力时，将本轮语音原话连同本次实时对话上下文送到 Codex 当前对话。仍支持明确说「让 ChatGPT 帮我写一份旅行计划」；不自动切换或新建对话，不再要求按确认键。
4. 可说「刚才的任务完成了吗」「告诉我刚才任务的结果」。实时对话保持开启时，设备会显示任务进度，并在空闲收听期间提示完成或等待授权。完成提示引用有限长度的公开回复摘要，不播报思考过程或工具输出；可能省略敏感内容。

普通问答、闲聊、讲故事和口头创作由 Pet 直接回答；家居、待办、CPU/内存状态、最新信息问答优先对应专用工具。在刚打开的网站里搜索或点击属于桌面操作，不改成全网资料检索。解释“如何操作”不等于要求执行；目标或指代不清时先澄清。涉及文件或项目时，Codex 当前会话仍须具备访问权限。既有按键语音输入仍是先写草稿、按确认键发送。

`desktop_agent` 提供 `capabilities/dispatch/status/result/cancel`，不开放模型指定任意程序、会话、路径或改写任务文本的参数。`capabilities` 只读本地已实现能力，不检测运行就绪，也不引入外部资料；不必每次先查，正常路由不增加额外模型轮次。桌面派发不与其他修改工具在同一批混发，避免原话中的操作重复执行。客户端权限与审批机制保持不变。

## 安全与一致性

- 设备对话在同一请求中选择真实工具或独立的 `pet_reply`，不把“我派给桌面助手”这样的自由文本当作派发凭据。执行前校验整批工具；异常决策只在尚未尝试任何工具时修正一次。普通回答无需真正调用桌面客户端。确认待执行的明确用户任务和完成通知后的致谢由模型按上下文区分，后者不应触发重做。该协议减少假承诺，并不保证模型永远正确理解任意表达。
- 派发不依赖宠物气泡的跟随会话。开始写入时锁定唯一的当前 Codex 窗口、输入框及标题/标题区域特征；窗口或编辑器变化、定位不唯一则停止本次输入，不影响旧任务，不擅自选择其他会话。只点击输入框附近唯一可用的原生 Send/Queue/Steer 按钮，执行中不再直接拒绝；不点击 Stop，不猜测快捷键，不自动批准授权。Queue 按排队提交表述，不承诺立即开始；Steer 可接入当前执行，具体行为由客户端决定。客户端复用同一编辑器且不暴露不同标题的切换仍有原生辅助功能识别边界，发送期间请勿切换对话。
- 不自动清空草稿，不改变 Codex 权限，不批准工具调用，不上传文件或任意历史会话。
- 派发和按键语音输入互斥，避免两个写入方同时修改输入框。提交前读回核对完整草稿；点击后的编辑器重绘不触发重新发送，实际接收由事件流中的新用户消息回执确认。发送回执不是任务完成回执。
- 已完成草稿写入的同设备按键语音可让出输入通道。释放时保留编辑器文字、与确认键原子互斥，不中断仍在录音、写入或发送的操作。ChatGPT 和 WorkBuddy 双端的新任务都把当前草稿完整引用在结构化 `existing_draft` 中，保留手动编辑及缩进；最外层 `current_user_request` 始终是本轮原话，并附完整语音上下文。嵌套的旧请求仅作资料，不能覆盖本轮要求；草稿仍可见不证明从未提交，结果不确定的旧操作须先核对，不得重放。快照包括 Agent、窗口和编辑器身份，写入前验证草稿没有变化；WorkBuddy macOS 保持受控原生粘贴和剪贴板恢复，Windows 保持原生 UIA 与单次写入，不确定时不重试。诊断记录固定失败阶段，不含窗口标题、草稿或原始系统错误。
- 同一语音轮次只派发一次。短时间内重复同一句话也复用回执；结果不确定时禁止自动重试。ChatGPT 和 WorkBuddy 共用原生输入串行队列，等待旧回执不阻塞新的明确请求；不同 Agent 的原生输入也不能并发抢占。每个 Agent 最多 8 条待处理请求。新任务成功、失败、取消或结果不确定都不结束旧任务的跟踪，不自动停止或重启旧任务。已明确失败或发送前取消的任务，在用户处理原因后可用新一轮语音重新委托。
- 不猜最近活跃会话：只接受派发前游标之后、匹配原始请求摘要的新用户消息来关联实际会话，再按对应会话、新任务起始和轮次标识确认结果。多个会话出现同请求回执时标为未确认；不根据任意完成事件认领结果。起始事件先于用户消息时只暂存最多 16 组标识，不保存事件正文。Bridge 重启、游标过期、事件丢失或跟踪超过 15 分钟时标为未确认，不编造完成。
- 网页、待办和其他 Agent 回复都是资料，不能授权新的桌面派发。结果查询轮禁止修改工具；派发后的口头确认使用本地固定回执。
- 语音「停」只打断播报。可以撤销尚未进入发送阶段的任务；已经开始发送或执行的任务需要到 Codex 原客户端取消。追加请求不等于撤回已经发出的操作。
- 退出实时对话不会撤回已发送的任务。默认 60 秒无交互仍会退出，退出后不主动启动语音播报；重新进入可查询本设备最近任务。任务最多保留 64 项且仅存内存，重启客户端后不恢复、不重放。

## 协议与隐私

追加请求使用相同的原话与上下文保护。实际新用户回执必须匹配请求摘要和会话；只有日志监控器明确记录 `turnActive=true` 才能把新请求关联到已在执行的轮次，不能只凭残留轮次 ID 推断已经开始。同会话新消息不再使旧请求变为 `continued`，旧请求仍等待自身回执；经过新用户回执证实、同一个已知活动轮次内的引导可以共享该轮最终回复，各任务结果分别保留，相同回复仅播报一次。不同轮次、不同会话、无活动证据的请求不能互相认领结果。Queue 可能直到出队才写入用户回执，因此不套用普通提交的 30 秒接收超时，但仍受 15 分钟总跟踪上限约束。无论原生提交是否返回成功，都不自动再次点击。

后续语音请求会附带同一设备、同一实时对话 15 分钟内的最近任务回执（仅内存中的有界公开摘要），放在最新用户消息之前的工具结果中，不提升为系统指令，不包含本地路径或 Codex 会话标识。模型据此区分对上一轮追问的明确答复和单纯进度查询；`done` 仅表示该轮结束，可能是一个澄清问题。仅凭 Agent 回复不能授权派发，「知道了」也不自动续做。单独查询状态或结果直接播本地回执，无需第二次模型总结。

真正派发时，原生层以 JSON 区分本次语音对话中的用户原话、Pet 回复、桌面回执、打断标记以及本轮请求，不由模型改写任务。例如「打开抖音」→「然后搜索 AI 硬件」→ Pet 澄清 →「是的」，最后一次发送会保留搜索要求与澄清问题，而非孤立的「是的」。历史用于理解指代，不作为待执行清单；已执行或未确认的操作不得因同步而重放。确认只适用于用户原本的明确要求，不能从 Agent 回复获得额外授权。

同步记录独立于模型最近 12 轮的滑动历史，仅存于当前语音会话内存，退出后释放；最多 128 条、12,000 字历史，序列化消息上限 28,000 字。超限停止派发并提示重新进入、明确重述任务，不静默裁掉确认所依赖的原始要求。新会话不附带旧会话记录，不包含系统人设、API 配置或原始工具数据。已有桌面回复沿用有界公开摘要，并非完整桌面日志。中断前已显示的 Pet 内容使用 `pet_partial` 标注“未完整播报”，用于衔接澄清，不等于用户已完整听到或操作已完成；未能识别的语音不能声称已同步。

兼容旧版 `event_msg:user_message` 和新版 `response_item:message` 的用户 `input_text`，两种镜像记录只计一次；developer/tool/assistant 和图像块不作为用户回执。请求摘要来自完整文字而非裁剪预览。点击发送后 UI 重绘或原生回读失败时进入等待接收状态，仍从发送前游标跟踪真实消息，不重复点击；30 秒无匹配用户回执才标为无法确认。成功接收、执行中和完成分开表述，完成播报可带公开回复摘要，不把“该轮结束”当作用户目标成功的证明。

Bridge 的 Codex 事件使用 `taskCorrelation.userHash`（实际发送的完整上下文消息去首尾空白后的 SHA-256）和 `taskCorrelation.turnId`。去重按本轮原话与最近一条不同的前序用户原话计算，不受 Pet 回复或工具回执变化影响；连续重复同一确认不重发，针对另一个明确用户任务的确认不误认成旧任务。派发中或结果未确认时仍拦截新任务。不为此扩大 240 字公开回复预览，不添加完整提示词或原始工具数据到事件或诊断日志。任务的设备、会话和文件路径只用于本地路由，不作为派发回执发给人设模型。

对话上下文随任务发送到用户当前打开的 Codex 会话，因此会出现在该客户端的聊天记录中。Pet 不新增持久化对话日志；自动完成提示直接使用本地回执和摘要。结果与其他工具一起查询时可能由用户配置的对话大模型总结公开摘要，单独查询使用本地回执。

## 验证边界

Rust 回归覆盖去重、忙碌与未确认状态保护、会话/请求/轮次关联、旧完成事件隔离、摘要过滤及参数白名单。Node 回归覆盖实际 Codex 日志监控器与 Bridge 有序事件流的请求摘要传递。编译与模拟测试不能代替 macOS/Windows 桌面输入、实体按键和真实语音的端到端验收。
