# petui 机制模式

本文件只用于检查机制完整性。它故意不提供完整 JSON、组件 ID、默认参数、实体坐标或可发布目录，不能把任何一节直接改名后当成组件交付。

## 使用方法

1. 先从用户原话独立写出目标、对象、输入、反馈、状态变化和结束条件。
2. 再用本文件检查是否漏掉运行时机制。
3. 所有 action 名、状态名、数值、布局和文案都必须根据当前需求重新设计。
4. 如果当前契约表达不了核心玩法，停止生成并明确指出缺少的能力；不要换成已有玩法。

## 通用状态机

- 初始状态要告诉用户当前可做什么。
- 组件库描述要让尚未启动游戏的用户看懂目标、核心规则和结束条件；实际操作由 `buttons.json` 映射生成，描述不写死可改绑的物理按键。
- 每个按钮 action 同时需要输入绑定、transition，以及可见反馈。
- 自动变化由 `tick` 或 `scene.tick_ms` 驱动，不能只写在说明文案里。
- 成功、失败、到点或完成必须有明确条件和结果状态。
- 结果状态必须提供重开、复位或下一步；退出由设备全局动作统一提供，不写入组件状态机或 `buttons.json`。
- 出厂默认全局退出是 SW3 短按（用户可以改绑或不绑定），生成或更新的包不得占用 SW3，也不得声明 `page_main/page_back` 等系统导航 action；画面提示统一写“全局键退出”，不得写死 SW3。
- 游戏将 SW1 作为开始/重新开始，把方向动作放到摇杆上/下/左/右；SW2 只在玩法确有射击、技能、暂停等次要动作时使用。
- 工具保留 SW1 主操作、SW2 次操作；需要切页、选择或数值调节时优先考虑四向摇杆。

## 坐标与动作游戏

- 只有确实需要位置、移动、碰撞或边界时才使用 `scene`。
- 先列出每类实体的角色，再决定数量、尺寸、起点、速度和边界策略。
- 玩家输入必须改变玩家能观察到的局面，而不是只切换 Dashboard 文案。
- 先检查四向摇杆是否能直接表达移动：上/下使用 `joystick.up/down`，左/右使用兼容事件 `knob.rotate_ccw/cw`；不要再用 SW1/SW2 代替方向键。
- 自动实体需要速度或 tick rule；离开边界后需要符合玩法的隐藏、重置、扣分、反弹或结束行为。
- 声称有碰撞时，必须声明对应的 `collision` rule 和可见后果。
- 一局至少具备开始、持续变化、玩家决策、即时反馈、结算和重开闭环。
- 玩家/主角先做透明背景 PNG，主要敌人和题材识别物在精灵配额允许时也做 PNG；平台、弹丸、金币和碰撞标记等次要几何元素再用 shape。若只能使用 shape，要写明能力或题材理由，不能默认退化成矩形和方块。
- 把横向 PNG 帧带逐帧裁开检查：默认首帧先看清主体，后续帧只做连续动作变化；任何空帧、裁切、重影、突然缩放或重心大跳都必须在发布前修正。
- action 不能只改变隐藏速度或内部变量。按下后应立即出现位移、生成物、状态/HUD 变化等可见反馈，随后才由 tick 延续运动。
- 发布前用 `smoke_test_widget_game.py` 自动探索真实 action，确认能开始、能操作、能推进、能得分/完成、能结算、能重开；任一环节不可达就回到机制设计修复，不能发布。
- 桌宠或互动摆件即使归类为 `tool`，只要声明了 scene，也要用同一脚本确认每个输入有可见反馈、互动后的 tick 能恢复或推进画面，不能借分类绕过场景自测。

### 射击类需求检查

- 为每类实体显式选择语义匹配的内置形状。飞机、敌机、弹丸、角色、云朵、金币等主体不得继续省略 `shape` 而退回矩形。
- 玩家战机默认使用受控 PNG sprite sheet；配额允许时主要敌机也使用 PNG。只有弹丸、命中特效、碰撞区等次要对象优先使用语义 shape；无法在 4 精灵、8 帧和 4096 总像素内清楚表达时再报告能力缺口，不得借用不相关形状或 Dashboard 图标冒充。
- 玩家移动必须由用户输入驱动，并受合理边界约束。
- 射击方式要匹配需求：自动射击需要持续产生或重置弹丸；手动射击需要独立 action。
- 弹丸与目标必须真实移动，命中必须由 collision rule 处理。
- 敌对对象需要独立的出现、移动、越界和再次出现逻辑。
- 撞击、漏过目标、生命耗尽或其他失败条件必须按用户需求实现。
- 不要因为需求包含“飞机”就复用固定车道、固定敌人数、固定网格或现成三态布局。

### 接取与躲避类需求检查

- 玩家移动方向、目标掉落方式和有效接取区域要独立设计。
- 接到、漏掉、撞到障碍分别产生与需求一致的反馈。
- 目标重置位置和节奏不能照搬其他游戏的常量。

## 计时与提醒工具

- 明确是正计时、倒计时、间隔提醒还是次数追踪。
- 时间变化使用 runtime tick 与整数变量，显示使用 `fmt_mmss` 或 `fmt_hms`。
- 区分运行、暂停、到点和复位；每个状态只展示真实可执行的动作。
- 完成次数只在真实确认动作后更新，不伪造历史数据。

## 数据展示工具

- 先确认数据来源、刷新频率、空态和断连态。
- 没有产品 bridge 提供的变量时，只能显示“等待数据”等诚实空态，不能生成伪实时值。
- 多页工具每页回答一个不同问题，避免复制相同指标填满槽位。

## 原创性检查

交付前逐项回答：

- 为什么是这些状态，而不是某个旧组件的状态？
- 为什么是这些实体、数量、坐标和速度？
- 每条 rule 对应用户哪一句需求？
- 删除任一核心 rule 后，用户要求的哪项玩法会消失？
- 是否存在只换了名称、文案、颜色或少量数值的旧组件结构？若存在，重新从空包设计。
- `visualStyle`、`visualPalette`、`visualLayout` 和实体 `shape/tone` 是否都能说明与当前题材的关系？若只是沿用默认组合，重新设计视觉方案。
- 与最近生成的其他游戏相比，是否仍是相同外壳、相同配色和相同实体轮廓？若是，不能发布。
- 用户没有明确要求复古/像素时，是否仍出现可见网格、硬直角方块主体或 8-bit 装饰？若是，改成 `clean`、语义轮廓、现代卡片层级和克制动效。
